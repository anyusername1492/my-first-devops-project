# Contributing to my-first-devops-project

Добро пожаловать! Этот репозиторий — учебный проект для отработки практик CI/CD и качества документации.

Перед тем как делать Pull Request или пушить в `main`, убедись, что твой вклад соответствует нашим стандартам. Пайплайн автоматически проверит всё ниже.

## Стандарты Markdown

Мы используем `markdownlint` для поддержания единого стиля. Обязательно соблюдай эти правила:

- **Заголовки:** главный заголовок должен быть первого уровня (`#`).
- **Списки:** перед и после списка должна быть пустая строка (правило `MD032`).
- **Пустые строки:** не оставляй две и более пустых строк подряд.
- **Длина строки:** ограничение по длине отключено (мы не хотим ломать длинные ссылки), но старайся не делать строки чрезмерно длинными без необходимости.

Если пайплайн падает с ошибкой `MDxxx`, читай лог — там будет точный номер правила и контекст.

## Проверка ссылок

Все ссылки в документации проверяются утилитой `markdown-link-check`.

- Не добавляй битые или заведомо нерабочие ссылки.
- Если ссылка ведёт на внутренний ресурс, убедись, что она доступна из CI (GitHub Actions работает в изолированной среде).

## Правила коммитов

Пайплайн проверяет сообщение последнего коммита:

- ❌ **Запрещено:** использовать `WIP` (Work In Progress) в сообщениях коммитов, отправляемых в `main`.
- ✅ **Рекомендуется:** писать понятные и короткие сообщения (минимум 10 символов), описывающие суть изменений.
- ✅ **Идеально:** включать номер задачи из трекера (если есть), например: `TASK-123: fix broken link`.

## Структура README

Файл `README.md` должен содержать:

1. Главный заголовок первого уровня (`# Title`).
2. Краткое описание проекта.
3. Список полезных ссылок (если применимо).
4. Инструкции по запуску/использованию (если применимо).

Мы автоматически проверяем, что в `README.md` есть хотя бы одна строка, начинающаяся с `#`.

## Что делать, если пайплайн упал

1. Зайди в **Actions** и открой упавший прогон.
2. Раскрой job `check-files` и найди шаг, который стал красным.
3. Прочитай сообщение об ошибке — оно максимально конкретное.
4. Исправь проблему локально.
5. Сделай новый коммит и запушь изменения.

> Важно: не использу `git commit --amend` и `git push --force` на ветке `main` после того, как коммит ушёл на сервер. Если пайплайн упал — добавь новый коммит-исправление. Это сохраняет прозрачную историю инцидентов.

## Как запустить проверки локально

Чтобы не ждать прогона в CI, ты можешь запустить проверки у себя на машине (требуется Node.js):

```bash
# Установка зависимостей
npm install -g markdownlint-cli markdown-link-check

# Проверка стиля
markdownlint .

# Проверка ссылок
find . -name "*.md" -type f -print0 | xargs -0 -n 1 markdown-link-check --quiet
